# 状态与恢复

## 1. 状态保存位置

| 数据 | 保存位置 | 恢复后 |
|---|---|---|
| 受控配置：策略、登记资产、模型配置、mask 规则 | PostgreSQL 配置库，版本化 | 保留 |
| 项目、环境、成员、资料 | 核心业务库 | 保留 |
| 会话与对话 | 核心业务库 | 保留 |
| 事实地图 | 事实库，带版本和证据 | 保留；新鲜度按原采集时间显示 |
| 执行申请、任务运行记录 | Harness 库 | 记录保留；在途的标为已停止 |
| 运维表格记录与日快照 | Harness 库 | 保留 |
| 调度计划 | 调度服务库 | 保留但暂停（Q4） |
| 审计 | 审计库，追加写 | 保留，不受容器删除或镜像回退影响 |
| V | 凭证库 | 保留；细节见 Q10 |
| 监控数据与告警 | 监控旁路自己的存储 | 不受核心恢复影响 |
| 临时产物 | 按任务隔离的临时目录 | 可回收，不作为唯一记录 |

删除容器不等于删除业务状态。所有持久状态都在容器外。

## 2. 恢复即停止（K-24）

就像重装客户端：对话都在，但正在跑的任务停了。

适用场景（Q5）：核心或 Worker 重启、Harness 或执行器重启、备份恢复、跨 VM 迁移。

### 2.1 恢复流程

1. 服务启动后先进入恢复模式。
2. 所有在途的执行申请和任务运行，状态改为"已停止（恢复中断）"。
3. 恢复前处于"执行中"的申请，改为"结果未知"，需要人工核对目标实际状态。
4. 调度计划全部暂停（默认，见 Q4）。
5. 生成恢复报告：停止的任务、结果未知的执行、暂停的计划。
6. 用户在工作台查看报告，决定是否重新执行或恢复计划。

### 2.2 重新执行

- 重新执行是一次新的运行，从头检验，不复用旧的检验结果和人工批准。
- 指纹会发现目标在中断期间的变化（K-04）。
- 既定任务不从中断的步骤自动续跑。需要从某步继续时，由用户选择起点，从该步重新检验。

### 2.3 不受影响的部分

- 预授权动作在目标本地运行，例如 systemd 按已审核的启动定义重启服务，不依赖平台（K-11）。
- 监控旁路继续采集、告警和通知（K-25）。

## 3. 一致性要求

恢复不续跑，所以不需要复杂的任务续跑机制。仍需保证：

- 状态变更用版本比较（CAS），防止并发覆盖。
- 调度周期有唯一周期键，同一周期不会重复提交。
- 执行器开始执行前先持久保存"开始执行"记录，恢复时据此判断"结果未知"。这条记录存在 Harness 库。
- 迟到的结果不能覆盖较新的记录。
- Worker 领取任务时可以用租约，防止两个 Worker 处理同一个任务。租约只用于领取，不用于恢复后接管或续跑。
- 事件可以用 outbox 投递：状态和待发送事件在同一事务写入，再由投递服务发出。outbox 只发通知，不触发执行，恢复后也不重放执行。

## 4. 跨 VM 迁移

1. 用户发起迁移，固定目标 VM、镜像 digest、配置版本和状态恢复映射。
2. 暂停调度计划，等待或停止在途任务。
3. 停止旧实例的核心、Worker、Harness 和执行器，确认已停止。无法确认时暂停迁移。
4. 备份状态，在新 VM 恢复。
5. 启动新实例，进入恢复模式（第 2 节）。
6. 切换入口，记录迁移审计。

同一逻辑实例同一时间只有一个活动实例。镜像回退不等于数据库或远端操作回滚。监控旁路在迁移期间继续运行。
